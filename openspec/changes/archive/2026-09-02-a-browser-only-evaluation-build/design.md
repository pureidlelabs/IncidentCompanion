# Scope

**An evaluation build is not an install, and it is not a route to one.** It has no operator, no store, no door and no account. Nothing a visitor does in it is carried into an install, and no requirement of `deployment` is answered by it.

**The set of things it demonstrates is open, and deliberately incomplete.** What it can honestly do it does; everything else it refuses. Growing the set is work, and each addition is a decision rather than a debt.

**One visitor, one case.** There is no second analyst, nothing arrives while a screen is open, and no two people share a state. The application's collaborative behaviour is outside what this form can show.

**The content is invented, and is not a claim about anybody.** What the evaluation build opens on describes no real incident, customer or person.

**Nothing here decides where a build is published or what publishes it.**

# Design

## The demonstration is the product, not a copy of it

The screens are the application's own. What is substituted is the boundary the application already has between itself and the thing that answers its requests — so a screen cannot behave differently in an evaluation build without behaving differently in an install, because it is the same screen taking the same shapes of answer.

Substituting anywhere further in would produce a second implementation of the client, and the first thing the two would disagree about is a refusal.

## Refusal is the default, and inclusion is the exception

Anything not deliberately included is refused. The alternative — answering what is not implemented with nothing — reaches the analyst as a screen that has drawn an empty state, which is indistinguishable from a real one and is the failure this capability exists to avoid.

That ordering is also what makes the build survive the application growing: a capability added later is refused by construction rather than by somebody remembering.

**What the build serves is checked against what the application asks for**, before publication rather than by a visitor. A route the application reaches that the build has neither included nor recorded as absent is a defect in the build.

## Judging a draft cannot be a second opinion

The rules an install judges a write by are the ones the evaluation build judges it by — the same rules, not a copy of them. A copy is a thing to keep in step, and the moment it drifts the build is teaching the analyst something the product does not do.

## What is shown is derived from the application, not written beside it

The case an evaluation build opens on, and anything else it must answer that an install would compute, are produced from the application rather than composed by hand. Written by hand, they are a second description of the product that ages while nobody is reading it.

## The visitor's work stays with the visitor

State is per-visitor and local to them. Nothing a visitor writes is published, reaches another visitor, or outlives their ability to discard it.
